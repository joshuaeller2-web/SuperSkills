# Evidence debugging

Use one debugging workflow instead of loading multiple overlapping debugging skills. Scale the work to the defect; a clear one-line failure does not need a ceremonial investigation.

1. Read the error, relevant project instructions and current code. Record the checkout, HEAD and dirty files before mutation. Preserve unrelated work. Check relevant recent changes and compare a working case when available.
2. Build the smallest practical command that reaches the user's symptom. Observe it fail for that symptom before changing code. A tool crash, missing dependency or unrelated error does not validate the probe. Read code as needed to build the reproduction. If the original environment is unavailable, continue useful static investigation but label the proposed cause UNVERIFIED and identify the missing evidence.
3. Minimize the failing input without removing the failure. For timing or intermittent defects, record attempts, failures and conditions; one successful retry is not a fix. For performance, measure the original operation under stated conditions before optimizing.
4. State plausible causes and predictions. Rank alternatives when the cause is ambiguous, then test one prediction and change one variable at a time. Trace the bad value backward through component boundaries. Capture only the fields needed to distinguish hypotheses; never dump credentials or an entire environment.
5. At the seam that reproduces the defect, keep the failing example as a regression. Use generated properties for a broad input space and an independent oracle or invariant rather than copying implementation logic. Make the smallest supported fix. Re-run the regression, the original scenario and relevant neighboring checks. Require a nonempty expected test inventory and reconcile collected, executed and skipped cases; `Ran 0 tests ... OK` is not verification. For an extracted package that intentionally omits tests, load external tests explicitly while asserting product imports resolve to the hash-bound package, rather than repeatedly discovering an empty directory or importing the editable repository.
6. If a proposed fix changes accepted behavior, severity or an existing test's meaning, follow the project's ruling review gate before implementing it. Do not quietly weaken, skip or rename a failing test. When browser negative cases intentionally return non-2xx responses, correlate allowed diagnostics to the exact request/status/test phase and retain unexpected network and resource failures as failures; blanket console-message-prefix suppression can hide real regressions. Verify that distinction with an unexpected-HTTP negative control before accepting a green run. If repeated attempts reveal different coupling problems, stop speculative edits and report the architectural evidence.
7. Remove only your temporary instrumentation within the authorized scope; preserve reusable repros and originals. Report the observed cause, files changed, exact commands and exit codes, covered/excluded inputs and remaining uncertainties. Use PASS, BLOCKED, UNVERIFIED, WITHHELD or SIMULATED for each requirement. Another agent grades the change when independent verification is required. Commit/push/merge/delete only with the user's authorization.

Use [references/techniques.md](references/techniques.md) when selecting a reproduction or when a failure spans services, timing, or performance.

When repairing a narrow process-execution allowlist, keep the invocation syntax constant and mutate the variables defining its executable payload, bootstrap, environment, paths, and limits. An unchanged call AST does not prove unchanged behavior. Bind the exemption to the reviewed behavior and retain these negative controls; use in-memory AST or isolated source fixtures when the gate can be tested without executing altered payloads. Hash the observed source and label helper-level probes separately from whole-package security acceptance.

For native credential and file-permission code, prove both allowed and denied paths in the exact locked, extracted runtime. Include a configured end-to-end request through the real credential reader and OS permission check, not only injected-token tests: a missing native API can reject every valid file while unconfigured and mock-authenticated flows remain green. Probe the actual binding and supported value comparisons rather than assuming that a Win32 C API name is exposed by its Python binding; never repair availability by weakening authorization.

When a harness error sidecar reports `SystemExit: 0`, inspect whether a broad `except BaseException` caught the runner's own deliberate successful exit. Reconcile the process exit code, assertions, import provenance and cleanup receipts before classifying the result; preserve the misleading sidecar as a reporting defect rather than converting it into a product failure or erasing it. Place deliberate exits outside broad exception handlers in any repaired test-only wrapper, and verify the classification with a bounded control.

For browser runners whose test fixture sanitizes environment variables, resolve the installed browser executable and launch options before fixture setup. An `undefined/Program Files` Edge discovery error after setup can be harness ordering rather than a missing browser. Preserve fixture isolation, pass the actual repository import path explicitly for external runners, and verify the corrected run instead of reinstalling browsers or weakening the environment boundary.
