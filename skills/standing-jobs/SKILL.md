# standing-jobs

Define the outcome, trigger, host, read sources, permitted changes, output, stopping conditions and review date. Reuse an existing matching schedule rather than duplicating it. Ask for a critical missing boundary, not repeated approval for already authorized actions.

Use the host's supported scheduling tool. Choose frequency from the requested cadence and data changes. Set bounded work and cost controls where supported; report unsupported controls instead of claiming they are enforced. Test the job's underlying command before scheduling when possible.

For monitors, distinguish no change, missing source, failure and actionable change. Preserve requested notification preferences. A scheduled report should show measurements and unknowns, not invent activity to fill a digest.

Recurring work retains the user's authorization boundaries. Do not treat scheduling as permission to send messages, spend money or deploy unrelated changes. Review stale jobs with their owner; quarantine or pause only within authorized scope.
