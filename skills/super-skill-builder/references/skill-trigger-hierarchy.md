# Skill trigger hierarchy

## Three distinct layers

1. **Standing behavior:** short rules supplied by the current host's active instructions. A library document describes the intended policy; it cannot prove that another host loaded or enforced it.
2. **Conditional package loading:** load a full SKILL.md or reference when its trigger matches, an explicit invocation selects it, or higher-priority host instructions require it. Do not load every package merely to satisfy lightweight controls.
3. **Observed activation and outcomes:** record actual loading and material use separately. File presence, an installation receipt, or self-reported use does not prove automatic activation or improved task quality.

## Five lightweight controls

These are intended per-request considerations where adopted by active host instructions, not five mandatory full-package reads or five automatic tool calls.

| Control | Standing consideration | Full package or tool trigger |
|---|---|---|
| adhd-focus | Honor the user's presentation preference without losing essential facts. | Load super-clear-answers for an applicable clarity/brevity task or a host-required match; do not impose brevity against the current request. |
| intent | Identify the current objective and authorization boundary. | No separate installed package is implied. |
| stack-router | Select an appropriate primary workflow. | Load stack-router when routing guidance is needed or required by the host; domain work loads its selected package. |
| lean-context | Avoid unnecessary context and preserve acceptance-critical details. | Load super-long-task for substantial work, context cleanup, or explicit token-efficiency requests, not routine one-step tasks by default. |
| memory-recall | Consider whether the request depends on earlier decisions. | Retrieve prior context only when relevant and permitted; do not force a memory search on every request. |

## Conditional domain skills

Domain packages load for their semantic triggers or explicit selection. For example, swarm-simulation concerns interacting simulated actors, super-decision-council concerns contrasting decision perspectives, and data-analysis concerns statistical analysis. Availability does not establish use.

## Usage recording

skill-usage-recorder is an end-of-request reporting workflow where the active host has adopted it. It does not replace the primary skill. Record only materially used skills and explicitly observed controls. Label agent self-report as such. Do not claim all five controls ran from a hardcoded list.

Verify automatic activation separately in each host/profile with a fresh-session natural-language request and its actual tool/session trace. Test both a positive trigger and a nearest non-trigger. An explicit skill_view call proves explicit loading for that call, not automatic activation across sessions.

## Examples

- A simple factual answer: preserve intent and presentation preferences; no forced long-task package, memory lookup, or council.
- A multi-stage software repair: software/debugging primary workflow, super-long-task when applicable, and only references matching the defect.
- A request to summarize a transcript: super-video-research; do not claim visual inspection from transcript evidence.

## Evidence boundary

Keep installed, discoverable, explicitly loaded, materially used (self-report), automatically activated (observed trace), and outcome-tested distinct. Grading records in Administration apply only to their tested cases and conditions. A usage count measures recorded usage, not effectiveness.
