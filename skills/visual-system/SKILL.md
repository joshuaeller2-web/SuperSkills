# Shared Visual System

Turn one design intent into consistent, editable outputs with evidence appropriate to each medium. This is a locally curated synthesis, not an upstream Archify skill or a vendor integration. See [source decisions](references/sources.md) for provenance and coverage.

## 1. Establish the brief

Identify the audience, main task, requested outputs, existing identity, functional facts, delivery destination, and constraints. Read an existing brief before making another. Use [the brief template](assets/brief-template.md) when starting from scratch; omit irrelevant fields.

Preserve supplied text, semantic relationships, measurements, interfaces, and brand decisions. Mark unknowns explicitly. Ask only when missing information changes the work materially; progress on independent work. Do not turn a review or concept request into implementation.

Identify which lanes are actually requested: UI, diagram, scene/game 3D, or fabricated 3D. Do not force every task to produce all lanes. Printable parts need manufacturing evidence; a scene render is a different deliverable.

## 2. Choose a coherent direction

Inspect relevant references before extracting their composition, hierarchy, typography, color roles, shape language, materials, camera, and motion. For video evidence, separate timestamped captions from frames actually inspected. Titles, thumbnails, and ads do not establish a demonstrated result.

If direction is open, propose a small, bounded set of distinct directions and recommend one against the brief. If direction is established, continue it. Match the fidelity and generation expense to the decision; make a sketch or one still before commissioning complex assets. A concept image demonstrates appearance only.

Record shared roles rather than forcing identical rendering values across media:

- Canvas, surface, readable foreground, action/selection accent, and explicitly labeled status colors.
- Type and label hierarchy, spacing rhythm, shape vocabulary, and meaningful contrast.
- A signature element, only if it helps recognition or the user's task.
- Motion purpose, camera rules, and a still/reduced-motion alternative where relevant.

Map these roles into medium-specific values. A UI color is not a guaranteed match to a lit material or a printed filament. Use actual render/export evidence to judge the appearance. Preserve real, readable text and labels; abstract marks are only optional decoration in non-instructional imagery.

## 3. Prove one representative slice

Build the smallest slice that exposes the main design risk: a primary UI flow with a difficult state, a diagram with a branch and real labels, a 3D object at its intended camera distance, or a fit coupon for a critical interface. When several media are requested, reuse the same real subject so their relationship is assessable.

Compare the slice to the brief. Record a specific finding and correction, with a screenshot, timestamp, semantic check, or measurement where appropriate. Resolve a repeated defect before multiplying it across screens, shots, nodes, or objects. Continue authorized reversible work without adding a blanket approval gate. Seek direction only if the alternatives materially diverge.

## 4. Produce through the correct lane

Read only the applicable sections of [production and acceptance](references/production.md). Discover available skills and tools rather than assuming an installation, login, model, or API exists.

- UI: use the installed UI/site workflow suited to the actual project. Design Studio can help explore identity if available; it is optional.
- Diagrams: use Archify when available for supported explorable diagrams; otherwise deliver an editable semantic format and honest preview.
- Scene/game 3D: use an available native scene/script workflow and test the export in its actual destination.
- Fabrication: use maker-3d or a comparable parametric workflow with measured requirements.

Prefer scripts/APIs for repeatable construction when suitable; use an available connector or UI control for actions they support better. Tool choice follows the operation, not a universal claim that scripting, MCP, or computer use is superior. Reference videos do not authorize software installs, subscription routing, credential changes, broad permissions, paid generation, or publication. Do not require Higgsfield or Blender to use this skill.

For motion deliverables, settle shot purpose, duration, aspect ratio, continuity, camera/action, and readable overlays; test a representative shot before a full render. Check asset rights before distribution. If generation is unavailable, use an appropriate still or code-driven alternative and state the limitation.

## 5. Review appearance and correctness separately

Inspect the current artifact, not just the prompt or a completion message. Use the brief and references for visual judgment; use the lane's acceptance checks for correctness. Do not turn aesthetic scores into measured usability, accuracy, physical strength, cost, or performance claims.

For substantial work, use a separate reviewer when authorized. Give the visual critic current outputs, audience/task, constraints, and relevant references without the author's rationale or previous grade. Give the technical reviewer sources and reproducible checks. Otherwise disclose self-review. Stop when the requested acceptance conditions are met; after repeated non-improving repairs, identify the remaining defect instead of inventing approval.

## 6. Hand off editable work and evidence

Deliver the requested artifact with its authoritative editable source, relevant exports, shared brief, and asset mapping. Keep stable names/IDs across representations where they carry meaning. Record source attribution and the exact revision reviewed. Include a concise result: what changed, what was observed, what remains unverified, and who owns the next action.

Distinguish PREPARED (files exist), REVIEWED (specified checks performed), INTEGRATED (tested in the stated destination), and PHYSICALLY TESTED (observed physical result). Never infer a later state from an earlier one. Use UNAVAILABLE with a reason for missing measurements or capabilities. Do not claim installation proves discovery, or structural validation proves live behavior.
